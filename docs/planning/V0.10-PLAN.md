# Gatekeeper v0.10 · 本地门禁升级计划（原 python-toolchain）

> 状态：设计已收敛（2026-10-30），待实施。本文件是唯一实施依据。
> 命名：插件定名 **gatekeeper**（机器标识全小写；界面标题 **Gatekeeper**；约定见第 14 节）。
> 依据：内部课程讲义《可复现工程与 CI》第八章（本地门禁）、第九章（detect-secrets）、第十三章（命令行闭环），配套参考工程 `reproducible_ci`。

---

## 1. 目标与用户要求

把插件从「能生成 lint/type/test/build 的门禁」升级为「与课程第八章 9 步流水线一致、且三处触发共用同一份定义」的门禁生成器与执行器。

用户原始要求（2026-10-30，m00119）：

| 步 | 命令 | 这一步证明什么 |
|---|---|---|
| 1 | `uv lock --check` | 依赖声明和锁文件一致 |
| 2 | `uv sync --locked --all-groups` | 本机已按锁文件恢复全部门禁工具 |
| 3 | `uv run --locked ruff check .` | 启用规则范围内没有 lint 错误 |
| 4 | `uv run --locked ruff format --check .` | 代码排版符合团队规则 |
| 5 | `uv run --locked mypy src packages/release_guard/src` | 主线源码满足类型契约 |
| 6 | `uv run --locked python scripts/validate_version_manifest.py` | Agent 版本证据完整且摘要一致 |
| 7 | `uv run --locked pytest --cov` | 行为测试通过且达到覆盖率门槛 |
| 8 | Secret 检查 | Git 跟踪文件没有未审核候选 Secret |
| 9 | `uv build --all-packages --out-dir dist` | 所有 workspace 包都能生成候选产物 |

附加约束：

1. 可对插件内提示词（skills 文档、工具 description、rationale）做修改升级。
2. 流程与配置参照第八章，**不得硬编码**：值从项目解析，模板只用于空项目。
3. detect-secrets 独立安装（`security` 依赖组），该步必须人工审核。
4. 版本清单内容与校验器按项目实际情况生成，不套用课程项目的九类组件。
5. 本地门禁集成成一个脚本，在 `git commit` 时触发。
6. 新构建的 `dist/` 必须覆盖旧产物。

后续追加（2026-10-30，m00234/m00272）：

7. **手动触发**必须能跑完整门禁（用于修理循环）；**自动触发**（commit）不得被慢阶段阻塞。
8. 插件要检测 commit 钩子是否已安装，并在 `py-audit` / 面板状态中提示 `prek install`。

## 2. 已确认决策（六分支 + 追加）

| 分支 | 选项 | 结论 | 理由 |
|---|---|---|---|
| 1 | 甲/乙 | **A：升级插件本身** | 任何项目经 `py-scaffold` 都能生成这套门禁，CI workflow 同步升级；不是只给某个项目写脚本。 |
| 2 | 甲/乙/丙 | **接收：8 阶段承载 9 步** | `sync` 在 CI 里本来就是安装依赖步骤，拆成独立阶段并渲染成 `Install dependencies`；`security` 改为 detect-secrets，pip-audit 降级为可选 `audit`。 |
| 3 | 甲/乙/丙 | **丙：第八章模板 + 只补缺失** | 新项目模板严格照第八章；已有项目配置一律保留、只补缺失项；同步改 `skills/modern-python` 与 `python-pyproject`，写成「课程默认口径 vs ALL 宽口径」。 |
| 4 | 甲/乙/丙 | **甲：单文件校验器** | `scripts/validate_version_manifest.py` 标准库实现，不建 `packages/release_guard`；支持 `--root`，项目测试可 import。 |
| 5 | 甲/乙/丙 | **甲：缺 baseline 即失败** | 生成器不代跑 `scan` / `audit`；缺 `.secrets.baseline` 时打印指引并退出 1，归 `environment` 而非 `findings`；审核完成后转绿。 |
| 6 | 甲/乙/丙 | **甲：commit 快子集** | 钩子只跑 `lock / lint / manifest / security(暂存区)`；`type / test / build` 交给手动全量与 CI。 |
| 手动形式 | A/B/C/D | **A：门禁脚本本身，默认 full** | 不生成包装脚本、不挂 prek 的 manual 钩子；手动门禁只依赖 uv + python。 |

核心原则：

- **单一事实源**：阶段目录（IR）→ 本地 `scripts/ci.py`、GitHub workflow、面板矩阵、工具输出，四者由同一份定义派生。
- **取值有来源**：每个从项目解析出的值都标注 `source`（`existing` / `detected` / `default:<值>`），dry-run 输出可见，不允许静默套默认。
- **人工审核点不可自动化**：`scan` 只是快照，`audit` 只能人做；摘要变更、Secret 判定同理。

## 3. 目标阶段矩阵（8 默认 + 5 可选）

| id | title | 命令（本地与 CI 同一 argv） | 证明什么 | 默认进 all |
|---|---|---|---|---|
| `lock` | Lock check | `uv lock --check` | 声明与锁一致，最便宜的失败 | ✅ |
| `sync` | Sync | `uv sync --locked --all-groups` | 本机按锁恢复全部门禁工具（CI 渲染为安装依赖步骤） | ✅ |
| `lint` | Lint | `uv run --locked ruff check .`<br>`uv run --locked ruff format --check .` | 规则内无错 + 排版达标（两件事分开报） | ✅ |
| `type` | Type check | `uv run --locked mypy <探测出的主线路径>`（项目已配 ty 则 `ty check`） | 主线源码满足类型契约 | ✅ |
| `manifest` | Version manifest | `uv run --locked python scripts/validate_version_manifest.py` | 版本证据完整、路径在根内、摘要一致 | ✅ |
| `test` | Test | `uv run --locked pytest --cov` | 行为测试通过且达到覆盖率门槛（门槛来自 pyproject） | ✅ |
| `security` | Secret scan | `uv run --locked python scripts/secret_scan.py` | Git 跟踪文件无未审核候选 Secret（只读，人工审核 baseline） | ✅ |
| `build` | Build | 先清空 `dist/`，再 `uv build --all-packages --out-dir dist`（非 workspace 退化 `uv build`） | 所有 workspace 包都能产出可安装候选物，旧产物不残留 | ✅ |
| `integration` | Integration tests | `uv run --locked pytest -m integration` | 需要真实数据库/网络的测试（无标记时跳过） | ❌ |
| `audit` | Dependency audit | `uv run --locked --with pip-audit pip-audit` | 锁定集合无已知漏洞（网络、噪音大，故可选） | ❌ |
| `container` | Container | `docker compose config --quiet` / `docker build --check` / `compose build` / `up -d --wait` / `ps -a` / `exec -T api id` / `down`（`if: always()`）+ 镜像体检 6 项（只报告） | compose 栈真能起、以非 root 运行；失败也清理 | ❌ |
| `release` | Release | 下载 quality 的 `dist` → attest → SBOM → upload → `gh release create`（不再自行构建；PyPI/镜像推送 optIn） | 产物可追溯，且发布的就是验证过的那一份 | ❌ |
| `deploy` | Deploy | checkout tag → `gh release view` → 部署命令（未替换即红）→ 条件探活 | 部署有可审计框架，且拒绝空绿 | ❌ |

顺序原则（第八章 8.2）：**快速确定、低成本先跑**。失败即停，修好后从失败项重跑，最终从头跑一遍（8.11）。

## 4. 三个触发入口（共用一份 IR）

| 入口 | 命令 | 跑什么 | 耗时 |
|---|---|---|---|
| 手动（修理） | `uv run --locked python scripts/ci.py` | 全 8 默认阶段，失败即停 | 几十秒 ~ 几分钟 |
| 手动（续跑） | `uv run --locked python scripts/ci.py --from test` | 从指定阶段开始，修好一项后不必从头 | 视阶段 |
| 本地自动 | `git commit` → `.git/hooks/pre-commit`（prek）→ `uv run --locked python scripts/ci.py --profile commit` | `lock / lint / manifest / security(暂存区)` | 几秒 |
| 远端自动 | `git push` / PR → GitHub Actions | 全 8 默认阶段（同一 IR 渲染） | 分钟级 |

`scripts/ci.py` 参数（生成物，标准库实现）：

- `--profile full|commit`：默认 `full`；`commit` 使用快子集，供钩子调用。
- `--from <stage>`：从指定阶段开始执行（新增）。
- `--stage all|lint,test`、`--stop-after <id>`、`--list`、`--json`、`--root`、`--timeout`：保留现有能力。
- 三条规范命令写入 `--help` 顶部、`py-scaffold` 的 next steps、README 三处。

CI 渲染规则：

- `sync` 阶段 → `Install dependencies` 步骤（`uv sync --locked --all-groups`），**删除** `lib/pipeline/github.js:344` 现有写死的同一行，改为由 IR 渲染。
- 顺序：`lock` → `sync` → `lint` → `type` → `manifest` → `test` → `security` → `build`，与本地一致。
- `build` 有产物时上传 `dist/`（`actions/upload-artifact@v4`，`if-no-files-found: error`）。

## 5. 取值解析规则（"不硬编码"的落地）

优先级：**项目现有 pyproject 配置（existing） > 目录/文件探测（detected） > 插件默认（default）**，每个值在 dry-run 输出中带来源。

| 值 | 来源判定 | 默认 |
|---|---|---|
| 类型检查器与路径 | pyproject 有 `[tool.mypy]`/mypy 依赖 → mypy；有 `[tool.ty]`/ty 依赖 → ty；路径取 `src/`、`[tool.uv.workspace].members` 下各包的 `src/`，探测不到则项目根 | mypy，路径由探测结果决定 |
| 覆盖率门槛 | `[tool.coverage.report].fail_under` | 新项目 90（第八章模板）；已有项目补配置时用 80（保守，避免一次加入就红） |
| ruff 行宽/规则集 | pyproject 现有 `[tool.ruff]` | 新项目：88 / `["E","F","I","B","UP"]` |
| 测试目录 | pyproject `[tool.pytest.ini_options].testpaths` → 探测 `tests/`、`test/`、`src/<pkg>/tests` | `tests`（探测不到时） |
| 构建方式 | `[tool.uv.workspace]` 存在 → `--all-packages`；否则普通 `uv build` | 由探测决定 |
| Python 版本 | `.python-version` → `requires-python` 下界 | 3.13 |
| 版本清单组件 | 探测 `prompts/`、`knowledge/`、`index/`、`eval/`、`src/`、`tests/` 等实际存在的组件 | 存在什么写什么，不伪造路径 |
| 状态基线 | `.secrets.baseline` 是否存在 | 不存在 → security 步给出指引并失败 |
| 镜像大小上限 | `[tool.gatekeeper.image].max_size_mb` | 缺失即不设上限（体检只报告，不拦截） |

## 6. 版本清单与校验器（甲：单文件）

产物（路径由插件固定，与 `scripts/ci.py` 同级约定）：

- `release/agent_versions.json`：清单。顶层 `schema_version / service / runtime / agent`；`agent` 下按探测结果记录组件。
- `scripts/validate_version_manifest.py`：标准库校验器。

生成规则：

1. 生成时扫描项目：`prompts/*.md`、`knowledge/`、`index/`、`eval/`、源码入口、`pyproject` 版本等。
2. 探测结果写入校验器顶部 `PROJECT_COMPONENTS` 常量（本项目实际要求的组件集合），清单只为这些组件写 `path + sha256 + version`。
3. `sha256` 由插件用 Node `crypto` 在生成时算出；生成结果打印每个摘要对应的文件。
4. `service.version` 取 `pyproject` 版本；组件初始 `version` 为 `<组件名>-1.0.0`。
5. **已有清单不覆盖**，只报告与磁盘的差异（丙原则）。

校验规则（对齐 8.8 的八类失败）：

| 场景 | 结果 |
|---|---|
| 正常清单 | 通过（打印服务名与版本） |
| JSON 损坏 | 失败："版本清单不是合法 JSON" |
| 顶层字段缺失 | 失败：指出缺失字段 |
| 组件缺失（`PROJECT_COMPONENTS` 中声明但清单没有） | 失败：指出组件名 |
| 文件不存在 | 失败："引用的文件不存在" |
| 路径越界 | 失败："路径越过了项目根目录" |
| 摘要不匹配 | 失败："摘要不一致：请审核变更后更新版本和 SHA-256"（不提供自动刷新） |
| 摘要匹配 | 通过 |

## 7. Secret 检查（detect-secrets）

- 安装：`[dependency-groups] security = ["detect-secrets>=1.5,<2.0"]`；不生成 `[tool.detect-secrets]` 段，配置只存在于 `.secrets.baseline`。
- 门禁步：`uv run --locked python scripts/secret_scan.py`。辅助脚本只做三件事：`git ls-files -z` 取跟踪文件（排除 `.secrets.baseline` 自身）→ 以 argv 调用 `detect-secrets-hook --baseline .secrets.baseline <files>` → 透传退出码。IR 不能表达 shell 管道，Windows 也没有 `xargs`，所以用脚本统一文件列表（第九章 9.7 明确允许）。
- 暂存区模式：`scripts/secret_scan.py --staged`（供 commit 钩子），对应 9.8 的 `git diff --staged --name-only --diff-filter=ACM`。
- **缺 baseline**：打印指引并以退出码 1 失败，归类 `environment`（不是 `findings`）——不是发现了 Secret，而是这一关无法判断。

```
Secret 检查未就绪：找不到 .secrets.baseline
只需人工完成一次（之后不再需要）：
  1) uv run --locked detect-secrets scan > .secrets.baseline
  2) uv run --locked detect-secrets audit .secrets.baseline   # 逐项 y/n/s/q
以后更新误报用：detect-secrets scan --baseline .secrets.baseline（不要用 > 覆盖，会丢失审核记录）
```

- hook 失败处置（9.9）：真凭据 → 轮换/删明文/查历史；误报 → 受控更新 baseline 并审查 Git 差异。生成器永不自动重建 baseline。

## 8. commit 钩子（自动触发）

生成的 `.pre-commit-config.yaml` 增加本地钩子（并移除 Yelp/detect-secrets 远程钩子，避免同一工具装两份）：

```yaml
  - repo: local
    hooks:
      - id: gatekeeper
        name: gatekeeper (commit profile)
        entry: uv run --locked python scripts/ci.py --profile commit
        language: system
        pass_filenames: false
        always_run: true
      - id: gatekeeper-secrets
        name: gatekeeper (secrets, staged)
        entry: uv run --locked python scripts/secret_scan.py --staged
        language: system
        pass_filenames: false
        always_run: true
```

- 安装：`uv tool install prek` → `prek install`（写 `.git/hooks/pre-commit`）。
- **安装检测**：`py-detect` 读取 `.git/hooks/pre-commit`，若不存在或未引用 prek，则在 `py-audit` 输出与面板状态中提示「配置已生成，但钩子未安装：运行 prek install」。
- 钩子不进版本库，每个 clone 需各自安装一次；跳过错提交用 `--no-verify`（文档说明，不鼓励）。

## 9. 配置模板口径（丙）

新项目（空项目）严格第八章：

- `[tool.ruff]`：`target-version = "py313"`、`line-length = 88`，`[tool.ruff.lint] select = ["E","F","I","B","UP"]`。
- `[tool.mypy]`：`python_version = "3.13"`、`strict = true`。
- `[tool.pytest.ini_options]`：`testpaths`、`addopts = "-ra --strict-markers"`。
- `[tool.coverage.run] branch = true`、`source = [...]`；`[tool.coverage.report] show_missing = true`、`fail_under`（值来自解析）。
- `[dependency-groups]`：`lint`（mypy、ruff）、`test`（pytest、pytest-cov）、`security`（detect-secrets）、`dev`（三个 include-group）。
- `[tool.uv] required-version`；workspace 项目追加 `[tool.uv.workspace] members` 与 `[tool.uv.sources]`。

已有项目：一律保留原配置，只补缺失项；每项输出标注来源；不覆盖、不迁移、不因本次改动改变已有行为。

文档同步：`skills/modern-python` 与 `python-pyproject` 中把 ruff 口径写成「课程默认（E,F,I,B,UP + 88） vs 宽口径（ALL + per-file-ignores）」两条，消除插件内部自相矛盾。

## 11. 测试与验收

插件内（必须全绿）：

1. `node test/smoke.mjs`：阶段目录、argv、workflow 文本、`ci.py` payload、profile 选择、manifest 校验器模板、secret 脚本内容、apply 白名单与幂等。
2. `node test/client.mjs`：面板、路由、状态字段、钩子安装状态。

dry-run 断言：

- 每个解析值带 `source`；空项目走模板；已有项目不变且只补缺失；已有清单不覆盖。

端到端（真实运行，不只看 dry-run）：

1. `reproducible_ci` 副本：其已有校验器/配置被保留；`security` 因缺 baseline 红（environment）→ 按指引 `scan` + `audit` → 转绿；`ci.py` 与 workflow 阶段一致。

## 16. job 结构分支决策（2026-10-30，grill 走查）

> 本轮追问起点（用户 m00289）：容器验收、发布、部署为什么各用单 job，单 job 与多 job 有什么区别。
> 本节结论优先于第 3 节表格中 container / release / deploy 三行。

| 子分支 | 结论 | 理由 |
|---|---|---|
| job 判据 | **甲：隔离单元** | 权限（写 token）、`environment` 审批、runner 能力（docker / self-hosted）、触发条件（仅 tag）任一不同才拆；并行只作次优先。本地单线执行与 CI 顺序语义保持一致 |
| quality 是否拆 | **不拆** | 共用一次 checkout + `uv sync`；阶段便宜且刻意 fail-fast；拆并行会让 lint 已失败时 pytest 仍在跑，且本地与 CI 的失败报告不一致 |
| 不生成 Dockerfile | **甲** | 插件不知道项目是服务还是 CLI、监听端口、需要哪些系统库；错的 Dockerfile 比没有更危险。模型=「你写 Dockerfile，我验」 |
| 镜像体检 | **6 项，只报告** | 大小、层数、默认用户（是否 root）、开发依赖泄漏（复用已起容器 `exec` 查 pytest/ruff/mypy）、有无 `.dockerignore`、是否多阶段。项目配置了上限才拦截，未配置永不失败 |
| container teardown | **修缺陷** | `compose-down` 的 `always: true` 只在本地 `ci.py` 生效；`lib/pipeline/github.js` 的 `stepLines()` 不渲染 `if: always()`，CI 失败后不清理（自建 runner 残留容器/网络）。修法：渲染 `if: always()`；`down -v` 保持注释 |
| release 产物 | **甲：复用 quality 的 `dist`** | 删除 `release-build`，改为 `actions/download-artifact@v4`；attest / SBOM / upload / `gh release` 用同一份产物，避免「验证过的包 ≠ 发布的包」；release job 因此不再需要 `setup-uv`；PyPI 发布与推镜像仍 optIn 默认关 |
| deploy 探活 | **甲：条件执行** | `deploy-smoke` 加 `if: vars.DEPLOY_HEALTH_URL != ''`，未配置显示 skipped，避免新项目部署 job 一上来就红。`environment: production` 保留 |
| deploy 占位未替换 | **甲：显式失败，不注释** | `deploy-run` 不再渲染为注释，而是真实的失败步骤：`echo "::error::部署命令未配置：把本步替换成你的部署命令"` + `exit 1`，`verified: false`、`local: false`。忘填 = 红（不是空绿）；填了真命令 = 转绿。理由：部署 job 全绿却什么都没部署，比红更危险 |
| 本地/面板表达 job | **甲：只标注不模拟** | `scripts/ci.py` 仍单线按序执行；`--list` 按 job 分组，执行到某阶段打印 `[job container] 需要 docker daemon`；面板维持 job 列。不在本地实现第二套 job 语义 |

镜像大小上限的配置位置（已定）：`pyproject.toml` 的 `[tool.gatekeeper.image].max_size_mb`；字段缺失即「不设上限」，体检只报告不拦截。放在 pyproject 而非独立配置文件，是为了与既有配置读取路径一致，不引入第二个配置源。
