# GitHub Actions Templates

CI/CD workflow patterns for this toolchain's Python projects: one gate whose default run is eight
stages drawn from a thirteen-stage catalog, and a release path that consumes the artefacts the gate
built.

## Purpose

Give a project a CI pipeline that **is** its local gate — same stages, same commands, same locked
toolchain — plus the delivery jobs that should only run after the gate is green.

## When to Use

Use this skill when:

- Setting up CI for a Python project managed with `uv`
- Deciding which stages run on every push and which are opt-in
- Wiring release artefacts (wheels, sdists, images) to a tag
- Fixing a workflow whose steps no longer match `scripts/ci.py`

When not to use it:

- The project is not Python/uv — the stage commands here assume `uv lock`/`uv sync`
- You need a bespoke deployment platform guide — `deploy` here is a placeholder on purpose

## The Gate: Nine Commands, Eight Default Stages (13 in the Catalog)

| # | Command | Stage |
|---|---------|-------|
| 1 | `uv lock --check` | `lock` |
| 2 | `uv sync --locked --all-groups` | `sync` |
| 3 | `uv run --locked ruff check .` | `lint` |
| 4 | `uv run --locked ruff format --check .` | `lint` |
| 5 | `uv run --locked mypy src` (or the project's checker) | `type` |
| 6 | `uv run --locked python scripts/validate_version_manifest.py` | `manifest` |
| 7 | `uv run --locked pytest --cov --cov-report=term-missing` | `test` |
| 8 | `uv run --locked python scripts/secret_scan.py` | `security` |
| 9 | `uv build --all-packages --out-dir dist` (or `uv build`) | `build` |

Run by default on every push and pull request:

```
lock → sync → lint → type → manifest → test → security → build
```

Opt-in, in the order they become relevant:

```
integration → audit → container → release → deploy
```

Four decisions worth remembering:

1. **Lock is proof, not preparation.** `uv lock --check` fails when `pyproject.toml` and `uv.lock`
   disagree, which is the only way to know the CI environment is the one the author tested.
2. **Sync is the install step.** There is no hand-written dependency installation command: the
   `sync` stage runs `uv sync --locked --all-groups` and is where dependencies come from.
3. **Security is a secret scan.** `scripts/secret_scan.py` (detect-secrets, locked, read-only) is
   the security stage; dependency auditing is the opt-in `audit` stage with `pip-audit`.
4. **Build produces the artefact release consumes.** `dist/` is uploaded once and downloaded by the
   release job — a second build at release time can differ from the tested one.

### Turning stages on

Optional stages are chosen at the call site, not in a config file. Pass a comma list to the tools
that render the workflow and the plan — `py-scaffold`'s `stages` argument and `py-audit`'s
`stages` — or preview it in the panel's `?stages=` query. The plugin configuration only owns two
toggles, `includeIntegrationGate` and `includeSecurityGate`; stages are not a config-file setting.

A typical call:

```json
{ "stages": "integration,container,release" }
```

`release` and `deploy` are only meaningful when a tag triggers them; `integration` needs a service
(a database) to talk to; `audit` needs a policy for what to do with a CVE.

## The Default Workflow

One quality job carries all eight default stages, in order. It is a single job on purpose: only then
can a green check mean "all eight steps ran on exactly this tree".

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install uv
        uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true

      - name: Set up Python
        run: uv python install 3.13

      - name: Lock check
        run: uv lock --check

      - name: Sync
        run: uv sync --frozen --all-groups

      - name: Lint
        run: uv run --locked ruff check .

      - name: Format check
        run: uv run --locked ruff format --check .

      - name: Type check
        run: uv run --locked mypy src

      - name: Version manifest
        run: uv run --locked python scripts/validate_version_manifest.py

      - name: Test
        run: uv run --locked pytest --cov --cov-report=term-missing

      - name: Secret scan
        run: uv run --locked python scripts/secret_scan.py

      - name: Build
        run: |
          uv run python -c 'import shutil,sys; shutil.rmtree(sys.argv[1], ignore_errors=True)' dist
          uv build --all-packages --out-dir dist

      - name: Upload distributions
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          if-no-files-found: error
```

Notes on the generated version of this job:

- **`--frozen` vs `--locked`.** CI renders `uv sync --frozen` (never re-resolves, installs exactly
  the lockfile) or `uv sync --locked` when the project configures locked mode. The local gate uses
  `--locked`; both mean "do not change the lockfile".
- **The coverage floor is not on the command line.** `pytest --cov` reads
  `[tool.coverage.report] fail_under` from the project. If a workflow passes a threshold on the
  command line, the workflow is the source of truth, not the project — fix the workflow.
- **Python comes from the project.** The version is the resolved `.python-version` (or
  `requires-python` lower bound); a matrix is only needed for a library that supports several
  interpreters.
- **`type` command follows the project.** `mypy src` is the default; a project that already uses
  `ty` renders `uv run --locked ty check src` and must not switch checkers as part of CI work.
- **The type paths come from the resolver.** `src` for a single package; every package's `src` for a
  workspace.
- **Only jobs that use uv install uv.** A release job that only downloads artefacts and calls
  `gh release` does not need `setup-uv`.

## Opt-in Jobs

### Integration tests

Tests that need a real service belong in their own job, never mixed into the default suite:

```yaml
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U test"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
      - run: uv sync --frozen --all-groups
      - name: Integration tests
        run: uv run --locked pytest -m integration
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/test
```

### Dependency audit

```yaml
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --frozen --all-groups
      - name: Audit dependencies
        run: uv run --locked --with pip-audit pip-audit
```

Keep this separate from the secret scan: a leaked credential and a vulnerable dependency have
different fixes and different urgency.

### Container build check

```yaml
  container:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - name: Validate compose file
        run: docker compose config --quiet
      - name: Lint Dockerfile
        run: docker build --check .
      - name: Build image
        run: docker build -t app:ci .
      - name: Start and probe
        run: |
          docker compose up -d --wait
          docker compose ps -a
      - name: Image report
        run: uv run --locked python scripts/container_report.py
      - name: Tear down
        if: always()
        run: docker compose down
```

`container_report.py` only fails when the project declares
`[tool.gatekeeper.image] max_size_mb` — the limit is project configuration, and with no limit the
report is informational.

The default-user fact comes from the image config (`Config.User`), which is why the container job
needs no `docker compose exec -T … id` step: identity is read where it lives, and no service name is
guessed.

## Release

The release job runs only on a version tag (or a manual dispatch), and it starts from the `dist`
artefact the gate produced. It never rebuilds.

```yaml
  release:
    needs: quality
    if: startsWith(github.ref, 'refs/tags/v') || github.event_name == 'workflow_dispatch'
    runs-on: ubuntu-latest
    permissions:
      contents: write
      id-token: write
      attestations: write
      packages: write
    steps:
      - uses: actions/checkout@v4

      - name: Download distributions
        uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist

      - name: Attest build provenance
        uses: actions/attest-build-provenance@v2
        with:
          subject-path: dist/*

      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          path: .
          format: spdx-json
          artifact-name: sbom.spdx.json

      - name: Upload release artefacts
        uses: actions/upload-artifact@v4
        with:
          name: dist-release
          path: dist/

      # Tag-only: publish to PyPI (repository secret PYPI_API_TOKEN or trusted publishing)
      - name: Publish to PyPI
        if: startsWith(github.ref, 'refs/tags/v')
        uses: pypa/gh-action-pypi-publish@release/v1
        with:
          password: ${{ secrets.PYPI_API_TOKEN }}

      # Tag-only: image (opt-in, requires container stage)
      - name: Log in to GHCR
        if: startsWith(github.ref, 'refs/tags/v')
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Push image
        if: startsWith(github.ref, 'refs/tags/v')
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.ref_name }}

      - name: Create GitHub release
        if: startsWith(github.ref, 'refs/tags/v')
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release create ${{ github.ref_name }} dist/* --generate-notes --verify-tag
```

Why provenance and SBOM before publishing:

- **Attestation** binds the wheel hash to this workflow run, so a consumer can verify the artefact
  was built by the gate rather than on a laptop.
- **SBOM** makes the dependency surface inspectable after the fact, when a CVE lands and you need
  to know which releases shipped it.
- **`dist/*` in the GitHub release** means the tested files are the downloadable files.

## Deploy

Deploy is a placeholder that **fails loudly** until the project fills it in:

```yaml
  deploy:
    needs: release
    if: startsWith(github.ref, 'refs/tags/v') || github.event_name == 'workflow_dispatch'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.ref }}

      - name: Verify release exists
        if: startsWith(github.ref, 'refs/tags/v')
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh release view ${{ github.ref_name }}

      - name: Deploy
        run: |
          echo "::error::部署命令未配置：把本步替换成你的部署命令"
          exit 1

      - name: Smoke test
        if: vars.DEPLOY_HEALTH_URL != ''
        run: curl -fsS --retry 5 --retry-delay 3 "${{ vars.DEPLOY_HEALTH_URL }}"
```

- **`environment: production`** gives the job its approvals and protection rules in the repository
  settings; a deployment without an environment bypasses them.
- **The placeholder exits 1 on purpose.** An empty deploy step that "passes" is worse than no deploy
  job: it reports a deployment that never happened.
- **The smoke test is skipped, not failed, without a URL.** `DEPLOY_HEALTH_URL` is a repository
  variable; when the project has no health endpoint the step must not invent one.

## Permissions

Every workflow starts from the minimum and adds what it uses:

```yaml
# Read-only workflows (lint, test, security, audit)
permissions:
  contents: read

# Release: create the GitHub release and push image tags
permissions:
  contents: write
  id-token: write
  attestations: write
  packages: write

# PR-commenting workflows
permissions:
  contents: read
  pull-requests: write
```

`permissions: {}` at the workflow level plus per-job grants is the strictest form and the one static
analysis of workflows prefers. Never leave the default (write-all) on a workflow that runs on
`pull_request`.

## Reusable Workflows

If several repositories share the same gate, extract the quality job into a reusable workflow and
keep the stage commands in one place:

```yaml
# .github/workflows/quality.yml
on:
  workflow_call:
    inputs:
      python-version:
        type: string
        default: "3.13"

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
      - run: uv python install ${{ inputs.python-version }}
      - run: uv lock --check
      - run: uv sync --frozen --all-groups
      - run: uv run --locked ruff check .
      - run: uv run --locked ruff format --check .
      - run: uv run --locked mypy src
      - run: uv run --locked python scripts/validate_version_manifest.py
      - run: uv run --locked pytest --cov --cov-report=term-missing
      - run: uv run --locked python scripts/secret_scan.py
      - run: uv build --all-packages --out-dir dist
```

```yaml
# caller
jobs:
  quality:
    uses: myorg/.github/.github/workflows/quality.yml@main
```

Pin the reusable workflow ref (`@v1` or a SHA) like any other action: `@main` turns an unrelated
repository's push into your build's problem.

## Caching and Speed

- `astral-sh/setup-uv@v5` with `enable-cache: true` caches the uv cache, which is where wheel
  downloads live; the `uv.lock` hash keys it.
- No `actions/cache` for `.venv`: `uv sync` against a warm cache is already fast, and caching a
  virtualenv across runs is a source of stale-environment bugs.
- `concurrency.cancel-in-progress` makes superseded pushes cheap.
- Lint/type/manifest are seconds; keep them ahead of `test` so the cheap failures surface first.
- Path filters (e.g. skip `test` on a docs-only PR) are acceptable only when a required check
  cannot be satisfied by a skipping job — GitHub treats a skipped required check as a failure.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `uv lock --check` fails in CI only | Someone edited `pyproject.toml` without re-locking | Run `uv lock`, commit `uv.lock` |
| `failed to fetch` during sync | Lockfile and `pyproject.toml` disagree, or `--frozen` used with a stale lock | Re-run `uv lock`, commit |
| Type step passes locally, fails in CI | Local venv has extra stubs; CI uses `--all-groups` | Run the gate locally with `uv run --locked` |
| Coverage fails with a different number | Threshold lives in the workflow, not `[tool.coverage.report]` | Remove the threshold flag; set `fail_under` |
| Secret scan fails with "baseline missing" | `.secrets.baseline` was never created | Create and audit it once, by hand; commit it |
| Release rebuilds the wheel | No `download-artifact` step | Download `dist`; never `uv build` in release |
| Image/hardening report passes despite a limit | Limit not in `[tool.gatekeeper.image]` | Declare `max_size_mb`, or accept informational mode |
| Deploy job never runs | Environment approval pending, or tag pattern mismatch | Check environment rules and `refs/tags/v*` |

## Rationalizations to Reject

| Claim | Reality |
|-------|---------|
| "The gate is eight steps, let's put them in eight workflows" | Then a red check does not tell you whether the whole gate ran on this tree; keep one quality job and split only waves that are genuinely optional |
| "CI can rebuild the wheel for release, it's the same source" | Not necessarily: a second build uses whatever the runner resolves; release must consume the artefact the gate tested |
| "Pass a coverage threshold in CI so it's explicit" | Then the project's `pyproject.toml` is not the standard, and local runs enforce something else |
| "Run pip-audit in the security stage so one red light covers security" | A leaked secret must be rotated, a CVE can be scheduled; merging them makes one of the two invisible |
| "A hand-written install step is clearer than sync" | Install is exactly what sync does, with the lockfile; a hand-written install is a second, unpinned way to build the environment |
| "Deploy step can be empty until later" | An empty deploy reports success; the placeholder must fail until it is implemented |

## Verification Checklist

- [ ] The workflow runs `uv lock --check` before anything that installs
- [ ] Dependencies come from the `sync` stage command, not a hand-written install step
- [ ] Lint runs both `ruff check` and `ruff format --check`
- [ ] The type step uses the project's resolved checker and paths
- [ ] `pytest` runs with `--cov` and no threshold flag; the floor is in `pyproject.toml`
- [ ] `scripts/secret_scan.py` runs in the `security` stage, after `test`, before `build`
- [ ] `dist` is uploaded as an artefact and downloaded (not rebuilt) by release
- [ ] Release is tag-gated and takes `needs:` from the quality job
- [ ] Attestation and SBOM run before publishing
- [ ] Deploy goes through an `environment`, with a placeholder that fails until replaced
- [ ] Workflow-level permissions are read-only; write grants are per job
